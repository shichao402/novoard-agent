# 需求文档：以契约为核心的协议面治理

## 引言

novoard 体系由 hub 与多个 agent 实现（Mac lite-agent、内网 lite-agent 等）组成。契约的单一权威源（SSOT）在 Novoard 仓 `docs/architecture/contracts.md` 与其下的 `docs/architecture/schemas/`，机器可校验格式是 9 张 JSON Schema（draft 2020-12）。agent 侧在 `src/contract/` 持有一份锁定拷贝，由 CI 做对比校验。

本需求同时作用于 **Novoard（hub）** 与 **novoard-agent** 两个仓库，改动不是集中在 agent 一侧。凡涉及 schema、校验器、门禁、契约文档的需求，两个仓库都必须改，只改一侧等于没改完。

该结构在设计上已经把契约当作核心资产，但实际核查发现六处断裂，使契约束缚力停留在"文档纪律"层面，未落到"机械约束"层面：

1. **契约结构与代码之间没有派生链路**。9 张 schema 定义了全部帧与数据的结构，但两个仓库的代码侧都没有任何由 schema 派生的类型定义，结构约束只能靠人工阅读文档与运行时校验兜住。写代码时把字段名拼错、把可选字段当必填、把枚举值写歪，在提交前都不会被发现。多对端场景下，这等于 N 份实现各自凭记忆对齐结构。
2. **文档承诺能加字段，schema 却禁止加**。契约文档声明 v2.1 只加可选字段、不带新字段的 2.0 agent 仍可注册；但 9 张 schema 全部使用 `additionalProperties: false`，任何未声明字段都会导致整帧被拒。文档与机器校验互相矛盾。
3. **校验失败静默丢弃，无任何回执**。hub 侧存在两处静默分支：信封校验失败时仅记录日志并返回；ops 帧 body 校验失败时同样仅记录日志并返回。两处都不发送 nack、不关闭连接。由于 body 校验排在 `type` 判定之前，`agent.hello` 携带未知字段时会直接落进第二处静默分支，agent 收不到任何响应，`registered` 恒为 false，进程表现正常但全部任务失败。次版本升级恰好落在这一场景。
4. **契约版本号多处独立维护，且其中一处被持久化**。hub 侧 `src/tunnel.mjs` 是 `"2.1"`，agent 侧门禁脚本是 `"v2.1"`（带前缀），agent 运行时配置是 `"2.1"`，三处字面不统一；更关键的是 agent 的 `agent.json` 会把版本号持久化，且读取顺序为配置文件优先。契约升级后，仅更新二进制而不重装的环境会永久停在旧版本号上握手失败。
5. **两仓无共享一致性夹具**。现有校验只能证明"两份拷贝完全相同"，无法证明"实现正确"。两边抄写完全一致但代码实现有误时，门禁仍然通过。hub 侧门禁已收缩为 SSOT 自检，agent 侧门禁才做跨仓比对，且比对对象是固定历史提交。
6. **门禁清单硬编码，新增 schema 不会被发现**。hub 的 `src/frames.mjs`、hub 的 `scripts/check-contract-copy.mjs`、agent 的 `scripts/check-contract-copy.mjs` 各自硬编码了同一份九个文件名清单。任一侧新增 schema 文件时，三处都不会因此报错，新增文件会被静默忽略。

同时，多对端是既定方向。契约要到 N 份实现之间真正收敛，仅靠"实现方凭默契抄写"不可行，需要契约具备可派生性、可判定性与可验证性。

本需求的目标是：把契约从"一份文档加一份拷贝"升级为具备五项机械约束的核心资产——可派生（从 schema 生成类型）、可演进（加字段不破坏）、可判定（拒绝必须明确回执）、可验证（跨实现跑同一批夹具）、单一来源（版本号只有一处）。

实施优先级按需求编号顺序，需求 1（schema 演进规则）最先，需求 2（类型派生）紧随其后。理由是先让契约本身具备可安全演进的结构，再建立"schema → 生成 → 代码"的派生链路。若顺序颠倒，schema 仍是封闭结构时，任何字段新增都会同时触发类型检查失败，让演进规则修订本身无法被验证。先改 schema，再做派生，则派生落地时契约已经是可演进的形态，两者互不干扰。

### 范围

纳入范围：帧与数据 schema 的演进规则、从契约 schema 派生 TypeScript 类型定义并在实现中生效、hub 与 agent 两侧的握手回执机制、契约版本号的来源收敛、跨实现一致性夹具、两个仓库的契约门禁口径修正、以及契约文档中兼容规则的对称性补全。

不纳入范围：A2A 正文格式变更（受 A2A spec 约束，保持 JSON-RPC 2.0）、二进制 wire format 迁移、将现有代码库整体改写为 TypeScript。

关于类型派生的形态说明：本需求不要求迁移语言。目标是在纯 JavaScript 代码库中，通过生成 `.d.ts` 声明并在源码中以 JSDoc 引用，配合可选开启的 JS 类型检查，获得结构层面的校验能力。语言迁移不在本期范围，但如果未来发生迁移，本期产出的类型定义应可直接复用。hub 仓的 `web/` 子项目本身是 TypeScript，但它不引用契约 schema，不在类型派生的范围内。

### 跨仓分工

以下表格说明每条需求在两个仓库的落点。实施时两个仓库都要改，任何一侧缺失都视为该需求未完成。

| 需求 | Novoard（hub，SSOT 持有方） | novoard-agent（锁定拷贝持有方） |
|---|---|---|
| 需求 1 schema 演进 | 调整 `docs/architecture/schemas/` 下九张 schema 的 `additionalProperties`；`src/frames.mjs` 放开帧层校验并保留未知字段 | 同步 `src/contract/schemas/`；同步 `src/contract/frames.mjs` 的校验逻辑 |
| 需求 2 类型派生 | 从自身 SSOT schema 生成类型，供 `src/` 以 JSDoc 引用 | 从锁定拷贝生成同一套类型，供 `src/` 以 JSDoc 引用 |
| 需求 3 拒绝回执 | `src/tunnel.mjs` 两处静默分支改为回 nack；扩展 `agent.hello.nack` 结构并纳入 schema | `src/tunnel-client.mjs` 增加 hello 确认超时与明确报错 |
| 需求 4 版本单一来源 | `src/tunnel.mjs` 的 `CONTRACT_VERSION` 作为唯一常量，统一字面格式 | `scripts/check-contract-copy.mjs` 的 `v2.1` 与 `src/config.mjs` 的默认值收敛到同一来源，清除 `agent.json` 持久化 |
| 需求 5 共享夹具 | 提供并维护夹具目录，纳入自身 CI | 消费同一份夹具，纳入自身 CI |
| 需求 6 门禁口径 | `scripts/check-contract-copy.mjs` 补强：schema 集合动态发现、跨仓一致性判定 | `scripts/check-contract-copy.mjs` 改为校验当前 SSOT 而非固定提交 |
| 需求 7 文档对称性 | `docs/architecture/contracts.md` 补双向兼容规则与主版本破坏点清单 | 无直接代码改动，承担验证职责 |
| 需求 8 可见性 | 状态端点返回契约版本 | 注册日志记录双方契约版本与 `msgId` |

## 需求

### 需求 1：契约演进支持向后兼容的可选字段新增

**用户故事：** 作为 agent 实现者，我希望在不升主版本的前提下给帧增加可选字段，以便新旧实现对端能够共存，而不是互相拒收。

#### 验收标准

1. WHEN 帧 schema 新增可选字段 THEN 系统 SHALL 接受不含该字段的旧帧，并接受含该字段的新帧。
2. WHEN 接收方收到含未声明字段的帧 THEN 接收方 SHALL 忽略该未知字段并继续处理，而非拒绝整帧。
3. WHILE 处理信封层（`v` / `kind` / `msgId` / `taskId` / `dedup`）时 THE 系统 SHALL 保持字段严格，未知字段仍被拒绝。
4. WHEN 契约新增字段 THEN 契约文档 SHALL 标注该字段为可选并注明引入的次版本号。
5. IF 契约需要删除字段、反转语义或缩减枚举 THEN 该变更 SHALL 升主版本，并 SHALL NOT 在次版本中以兼容名义引入。
6. WHEN 调整 `additionalProperties` 策略 THEN 该调整 SHALL 与契约文档 §0 的版本兼容声明保持一致，不得出现文档承诺可加而 schema 拒绝的矛盾。
7. WHEN 帧类 schema 放开未知字段 THEN hub 侧与 agent 侧的校验器 SHALL 在通过校验后保留未知字段的原值，以便转发场景不丢失对端扩展信息。
8. WHEN 修改任一张 schema THEN hub 侧 `docs/architecture/schemas/` 与 agent 侧 `src/contract/schemas/` SHALL 保持逐字节一致，且两侧校验器逻辑 SHALL 保持等价。
9. IF 某张 schema 因安全或语义原因必须保持封闭 THEN 该 schema SHALL 在契约文档中显式标注为例外，并说明理由。

### 需求 2：从契约 schema 派生 TypeScript 类型

**用户故事：** 作为 agent 与 hub 的实现者，我希望类型定义由契约 schema 自动生成而非手写，以便代码结构与契约保持一致，且契约变更时结构漂移能被机械捕获。

#### 验收标准

1. WHEN 契约 schema 发生变更 THEN 系统 SHALL 能够通过单一命令重新生成全部 TypeScript 类型定义，无需人工编辑生成物。
2. WHEN 生成 TypeScript 类型定义 THEN 生成 SHALL 覆盖 9 张 schema 的全部对象、枚举、必填字段与可选字段，并对 `additionalProperties: false` 表达出对应的类型约束。
3. WHEN 生成物已存在而 schema 已变更 THEN CI SHALL 失败，并指出生成物与 schema 不一致。
4. WHEN 实现代码引用契约类型 THEN 该引用 SHALL 通过 JSDoc 注释指向生成的类型，并 SHALL 在启用 JS 类型检查时被校验。
5. WHEN 在启用 JS 类型检查的情况下代码使用了 schema 中不存在的字段、类型不符的字段值或缺失的必填字段 THEN 类型检查 SHALL 报错。
6. IF 生成器遇到无法映射的 schema 关键字 THEN 生成器 SHALL 明确报错并指出该关键字与所在 schema，而非静默生成不完整的类型。
7. WHEN 多个 agent 实现共用同一契约 THEN 各实现 SHALL 使用同一份生成的类型，而 SHALL NOT 各自手写等价定义。
8. WHEN 生成产物被提交到仓库 THEN 该产物 SHALL 标注为机器生成，且 SHALL NOT 允许手工修改。
9. WHEN 生成类型 THEN 生成 SHALL 反映需求 1 调整后的 `additionalProperties` 策略：帧类为开放式结构，信封层为封闭结构。
10. WHEN hub 与 agent 分别生成类型 THEN 两侧生成物 SHALL 来自同一份 schema 内容，且 SHALL 在 CI 中校验两侧生成结果等价，不得因生成器配置差异产生分歧。

### 需求 3：契约拒绝必须显式回执

**用户故事：** 作为运维者，我希望契约不兼容时得到明确报错，以便区分"对端没理我"和"我发错了"，而不是面对一个进程正常但全部失败的黑箱。

#### 验收标准

1. WHEN hub 校验 `agent.hello` 失败 THEN hub SHALL 回送 `agent.hello.nack`，携带失败原因与 hub 侧契约版本。
2. WHEN hub 校验其他类型的帧失败 THEN hub SHALL 回送携带该帧 `msgId` 与失败原因的回执。
3. WHEN agent 发送 `agent.hello` THEN agent SHALL 在有限超时窗口内等待确认或拒绝。
4. IF 超时窗口内未收到任何回执 THEN agent SHALL 报告"疑似契约不兼容"，并 SHALL 以可识别的失败状态终止或重试，而非保持静默连接。
5. WHEN 回执携带失败原因 THEN 该原因 SHALL 包含可用于定位的具体字段路径，而非仅给出笼统错误。
6. IF 拒绝原因为主版本不匹配 THEN 回执 SHALL 同时携带双方主版本号。
7. WHEN hub 校验信封失败且无法解析出 `msgId` THEN hub SHALL 回送不带 `msgId` 的错误回执，或关闭连接并给出可读的关闭原因，SHALL NOT 仅记录日志后静默返回。
8. WHEN hub 校验 ops 帧 body 失败 THEN 该分支 SHALL 在能判定帧类型时回送针对该类型的 nack，SHALL NOT 在类型判定完成之前就丢弃帧。
9. WHEN 回送 `agent.hello.nack` THEN 该帧结构 SHALL 由 schema 约束，并 SHALL 包含失败原因、hub 契约版本与可选的可重试标记。

### 需求 4：契约版本号单一来源

**用户故事：** 作为维护者，我希望契约版本号只有一个权威来源，以便升级契约时不必同步修改多处、也不必担心存量安装被固定住。

#### 验收标准

1. WHEN agent 建立连接 THEN `contractVersion` SHALL 来源于契约常量，而非用户可编辑的配置。
2. IF 已有安装的配置文件中存在历史版本号 THEN 系统 SHALL 以契约常量为准，并 SHALL 在版本不一致时清理或忽略该持久化值。
3. WHEN 契约版本发生变更 THEN 该变更 SHALL 只需修改单一来源即可生效，无需修改其他文件。
4. WHEN 版本号跨边界传递（契约文档、两侧门禁脚本、两侧运行时） THEN 各处的字面格式 SHALL 统一，不得出现带 `v` 前缀与不带前缀混用。
5. IF 门禁脚本或运行时检测到版本号不一致 THEN 系统 SHALL 明确报错并指出不一致的两处位置。
6. WHEN hub 更新 `CONTRACT_VERSION` THEN 该变更 SHALL 触发 agent 侧同步要求，且任一侧未同步时 SHALL 使门禁失败，而 SHALL NOT 由 agent 侧单方面维持旧值继续通过。
7. WHEN 契约版本升主版本 THEN 已有安装的持久化版本号 SHALL 被自动纠正或忽略，SHALL NOT 要求用户手工修改配置文件。

### 需求 5：跨实现共享一致性夹具

**用户故事：** 作为协议维护者，我希望所有实现跑同一批帧样本并得出同一结论，以便捕获"抄对了但写错了"这类字节比对发现不了的问题。

#### 验收标准

1. WHEN 契约变更 THEN 契约仓 SHALL 提供一组版本化的帧样本，覆盖合法帧与非法帧两类。
2. WHEN 任一实现运行该样本集 THEN 该实现 SHALL 对每个样本得出与预期一致的结论（通过或拒绝）。
3. IF 某实现对任一预期的结论不一致 THEN 该实现的 CI SHALL 失败。
4. WHEN 新增帧类型 THEN 样本集 SHALL 同步新增该帧的合法与非法样本。
5. WHEN 实现之间发生了字节比对无法区分的语义偏差 THEN 样本集 SHALL 能将其暴露为测试失败。
6. IF 样本集与 schema 版本不匹配 THEN 校验 SHALL 明确报错，而非静默跳过。
7. WHEN hub 侧与 agent 侧消费同一份夹具 THEN 两侧 SHALL 以相同方式加载，SHALL NOT 各自维护副本。

### 需求 6：契约门禁反映当前 SSOT 而非历史快照

**用户故事：** 作为维护者，我希望契约门禁校验的是"当前是否一致"，以便门禁通过真正代表与 Hub 现状一致，而不是只与某个旧提交一致。

#### 验收标准

1. WHEN 执行 agent 侧契约门禁 THEN 校验 SHALL 覆盖 schema 逐字节一致、契约文档版本号正确、校验器行为自检三项。
2. WHEN Hub 侧新增 schema 文件 THEN 两侧门禁 SHALL 均失败并提示该文件名，而非因硬编码清单而静默通过。
3. WHEN 门禁通过 THEN 该结果 SHALL 能代表当前 SSOT 状态，而非仅代表某个固定历史提交的状态。
4. IF 门禁所依据的 SSOT 来源不可达 THEN 门禁 SHALL 明确报告不可达，而非默认通过。
5. WHEN 执行 hub 侧契约门禁 THEN 校验 SHALL 覆盖：schema 集合按目录动态发现、schema 合法性、校验器行为样例，以及跨仓一致性判定入口。
6. WHEN schema 文件被删除或重命名 THEN 两侧门禁 SHALL 失败并指出缺失的文件名，而非仅因剩余文件齐全而通过。
7. WHEN 门禁失败 THEN 输出 SHALL 指明是哪个仓库、哪个文件、哪一侧未同步，以便直接定位需要补改的位置。

### 需求 7：契约文档补全双向兼容规则

**用户故事：** 作为新接入的 agent 实现者，我希望契约文档明确说明两个方向的兼容规则，以便判断"老客户端连新服务"和"新客户端连老服务"分别会发生什么。

#### 验收标准

1. WHEN 契约文档描述版本兼容 THEN 文档 SHALL 同时说明"旧实现连新服务"与"新实现连旧服务"两个方向的行为。
2. WHEN 次版本新增可选字段 THEN 文档 SHALL 明确说明旧实现遇到新帧时的预期行为（忽略或拒绝），并与 schema 实际行为一致。
3. WHEN 文档中的 wire 示例与 schema 冲突 THEN 冲突 SHALL 由 CI 检出，而非依赖人工评审。
4. WHEN 主版本升级 THEN 文档 SHALL 列出该主版本的具体破坏点清单。
5. WHEN 契约文档变更 THEN 该变更 SHALL 落在 Novoard 仓的 `docs/architecture/contracts.md`，agent 侧 SHALL NOT 维护第二份语义描述。

### 需求 8：契约变更的可见性

**用户故事：** 作为运维者，我希望能够查询当前运行实例的契约版本，以便在出现不兼容时快速定位是哪一侧落后。

#### 验收标准

1. WHEN 查询 hub 的健康或状态端点 THEN 返回 SHALL 包含当前契约版本。
2. WHEN agent 完成注册 THEN 日志 SHALL 记录本次握手使用的契约版本以及 hub 侧契约版本。
3. WHEN 发生契约拒绝 THEN 两侧日志 SHALL 都能定位到同一 `msgId`，便于关联排查。
4. WHEN agent 启动并读取到配置中的历史版本号 THEN 日志 SHALL 提示该值已被契约常量取代。

## 边界情况

1. 存量安装的 `agent.json` 中已写入旧版本号，升级后必须能自动纠正，不得要求用户手工修改文件。
2. 在契约门禁固定历史提交到切换到当前 SSOT 的过程中，可能存在短暂的校验口径不一致，需明确过渡方式。
3. 帧放开未知字段后，字段名拼写错误将不再被拒收；该损失由需求 2 的类型派生在编译期补偿，因为类型层仍会拒绝未声明字段。
4. 若某实现对端暂时无法升级，回执机制会导致其立即暴露为失败，而非像现在这样静默运行。这是预期行为，但需要在发布说明中明确告知。
5. `agent.hello.nack` 本身也受 schema 约束，其结构变更需遵循同样的演进规则，不能成为绕过约束的例外通道。
6. 需求 1 与需求 2 的落地顺序不可颠倒。若先落类型派生而 schema 尚未放开，生成的类型会把帧表达为封闭结构，此后任何字段新增都会同时触发类型检查失败，使演进规则修订本身无法被验证。
7. 生成物纳入版本控制后，schema 微调都会产生生成物 diff。该 diff 应被视为正常产物并自动生成，不纳入人工评审关注范围。
8. 若生成器与 schema 演进节奏不同步，可能出现生成器不支持新关键字的情况。此时必须显式报错并阻止合入，不得生成部分类型。
9. 帧放开未知字段后，若实现将整帧原样转发，未知字段会被一并透传。这通常是期望行为，但需要在转发路径上确认不会因此放大无效数据。
10. 两个仓库的校验器与门禁脚本各自硬编码了同一份九个文件名清单，新增 schema 时三处都要改且都不会因此报错。这是本需求要消除的重复来源，实施时须改为目录动态发现，不能保留任何一处手工清单。
11. 两个仓库的改动需要配套发布。若先发 hub 后发 agent，或反之，中间窗口内可能出现一侧已放开未知字段、另一侧仍拒绝的情况。需在发布说明中明确该窗口的行为，并确认窗口内不会产生静默失败。

## 成功标准

1. 新增一个可选字段时，无需升主版本、无需改动任何实现，所有实现对端正常互通。
2. 契约文档声明可加字段与 schema 实际行为一致，不再出现文档承诺、schema 拒绝的矛盾。
3. 手工把代码里的契约字段名改错后，类型检查报错，无需等到运行时。
4. 修改任一 schema 字段后，两个仓库重新生成并提交生成物；若任一侧忘记重新生成，CI 直接失败并指出差异。
5. 人为制造字段级不兼容时，agent 侧在超时窗口内给出明确报错，而非静默失败。
6. 契约版本号在两个仓库中只有一处可编辑来源，升级契约只需改该处，且字面格式统一。
7. 任一实现故意篡改校验逻辑后，共享夹具能将其捕获为 CI 失败。
8. Hub 新增或删除 schema 文件后，两个仓库的门禁都失败并提示文件名与未同步的一侧。
9. 契约文档所描述的行为与 schema 实际行为在 CI 中始终保持一致，不再依赖人工发现矛盾。
10. 任一仓库单独修改契约而未同步另一侧时，门禁明确指出是哪个仓库、哪个文件需要补改。
