# 发布说明模板（hub 与 agent 共用）

契约变更时，两仓发布说明都必须包含「契约与配套发布」一节。目的是让升级的人在一眼之内知道：这次能不能只升一侧、先升哪一侧、不升的另一侧会看到什么。

## 为什么要有这一节

契约是两个独立发布的产物之间的唯一约定。契约变更若只升一侧，另一侧的失败形态通常不是"报错退出"，而是"看起来正常但结果不对"——字段被忽略、任务永远不完成、连接挂着不注册。有了固定的一节，升级前就能判断风险，而不是上线后翻日志猜。

## 逐字复制以下模板

```markdown
## 契约与配套发布

- 契约版本：vX.Y（上一版 vX.Y）
- 变更级别：次版本（向后兼容） / 主版本（破坏兼容）
- 本仓变动的契约面：schema / 校验器 / 帧类型 / 字段语义（列出具体项）

### 单侧先发时的行为

| 先发的一侧 | 未升级的一侧会看到 |
| --- | --- |
| hub | （写具体表现：哪些帧被忽略、哪些字段缺失、任务是否照常完成、日志里会出现什么） |
| agent | （写具体表现） |

### 建议发布顺序

- 次版本：（通常任意顺序，写清是否真的任意）
- 主版本：先 hub 后 agent；hub 本版支持的 agent 最低主版本为 vX

### 升级后如何确认生效

- hub：`GET /api/status` 的 `contractVersion` 应为 vX.Y
- agent：启动日志应出现 `已注册到 hub（msgId=...，本端 contractVersion=vX.Y，hubVersion vX.Y ...）`
- 两侧日志的 `msgId` 应能对上同一次注册

### 回滚

- 回滚到上一版是否有遗留影响（已写入的新字段、已升级的本地状态文件格式等）
```

## 填写要求

- 「单侧先发时的行为」不能写"不兼容"这种结论性词，要写观察到的现象。例如写"agent 的 `telemetry` 新指标被 hub 忽略，面板上看不到该指标，任务不受影响"，而不是写"telemetry 不兼容"。
- 主版本发布必须在表格里明确写出 `agent.hello.nack` 的 reason（`contract-major-mismatch`），因为这是对端唯一能看到的明确信号。
- 若本次没有任何契约面变动，仍保留该节，写「契约版本：vX.Y（未变）」并省略表格。空着不写会让人无法区分"没变"和"忘了写"。
