# ADR-0011: 任务表只在内存，重启即清

- 状态：Accepted
- 日期：2026-10-20
- 讨论来源：ADR 重新整理时补记。此前文档只说"任务表在内存"，未说明为什么不落盘

## Context

`local-a2a.mjs` 的任务表是一个 Map：

```js
function createLocalTasks() {
  const tasks = new Map();
  return { put, get, list, lastOf };
}
```

它服务于三个用途：磁贴的"上次运行"、SSE 的订阅快照、`tasks/get` 的查询。

进程重启后这张表就空了。表现是：磁贴回到"尚未运行"，`tasks/get` 对旧 taskId 返回 not found。

历史运行记录并没有丢：`state/shortcuts/<target>/<taskId>.jsonl` 保存了每次运行的输出，保留 30 天（`SHORTCUT_LOG_RETENTION_MS`），`/api/shortcuts/:id/runs` 能列出来。丢的只是"状态"这一层。

## Decision

任务表只在内存，不落盘。重启后磁贴回到"尚未运行"，历史输出仍可查。

理由是这个进程的生命周期与任务生命周期基本重合：sidecar 退出即意味着所有运行中的子进程已被取消（`shutdown` 会 `runner.cancel()` 并等待回收）。没有"重启后继续跑"的任务，也就没有"重启后需要恢复的状态"。

配套约定：

- 状态只保证在 sidecar 生命周期内有效，这一点要写进文档与排障手册，避免用户以为丢了数据。
- 需要跨重启追溯时查 `state/shortcuts/`，不是查任务表。
- Hub 侧对未完成任务的补偿由 Hub 负责重新下发，不期望本机记得。本机对 `duplicate-taskId` 的处理只覆盖同一进程内的重复投递。

## Consequences

- 收益：没有状态持久化代码，也没有"内存与磁盘不一致"这类问题。
- 收益：进程退出即干净，不需要恢复流程与版本迁移。
- 代价：重启后无法回答"上次那个任务最后怎么了"。要回答只能翻日志，且日志里没有结构化的终态。
- 代价：磁贴的"上次运行"是易失的。用户重启后看到"尚未运行"，可能误以为从未跑过。
- 代价：Hub 重放已结束任务时会重新执行（因为 `running` 里没有它）。当前依赖 Hub 只重放未确认帧；若 Hub 策略变化，需要本机加已结束任务的幂等表。
- 被否决的方案一：把任务表落成 JSONL 或 SQLite。会引入恢复流程、schema 版本、清理策略；而收益只是"重启后能看到上次状态"，与 `state/shortcuts/` 的信息高度重叠。
- 被否决的方案二：落盘但只存最近 N 条。仍需清理与恢复逻辑，收益不足以抵成本。
- 被否决的方案三：把状态写进 `shortcut-log` 的同一份文件。会让"给人读的输出"与"给机器读的状态"混在一起，两者的保留策略与解析方式都不同。
