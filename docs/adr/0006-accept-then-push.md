# ADR-0006: 受理即回执，进度与终态靠推送

- 状态：Accepted
- 日期：2026-10-20
- 讨论来源：2026-10-20 讨论。现状是命令送达就算完成，用户看不到执行状态

## Context

本仓有三条触发链路，都以"命令送达"为终点，而不是"执行结束"：

1. 控制台点击：`run()` 在 `finally` 里 `setPending(null)`，HTTP 一返回按钮就恢复可点。
2. 本机 A2A：`novoard_run_target` 发出 `message/send`，拿到 taskId 就返回，是纯 fire-and-forget。
3. 对等触发：`peer.watchRun` 只记 taskId，终态由 `reportRun` 回一句"已结束"。

问题的实质不是"没有状态"，而是"没有把状态送到需要它的人手上"。`/plan` 这类任务跑几十秒到几分钟，中间没有任何东西告诉用户还在跑。

需要决定的是：调用方应该在什么时候拿到结果。

## Decision

采用"受理即回执 + 推送汇报"：

- 触发请求只负责受理。回执必须已包含 `taskId`、当前状态、以及可订阅进度的通道。
- 状态变化由服务端推送，调用方不从"请求是否返回"推断执行是否完成。
- 终态必须送达。推送不可用时以查询快照兜底，不允许"任务结束了但没人知道"。

一条不可协商的约束：回执返回前，任务必须已经落在任务表里。否则调用方拿到 taskId 立刻订阅，会撞上"查不到这个任务"的空窗。

对 A2A 场景的额外约定：`/plan` 这类长任务不占住调用方的一轮，立刻回执，后续靠推送汇报。理由是 HTTP 与 A2A 都有超时上限，等终态会在超时后返回一个既无结果也无进度的错误，比"不知道进度"更糟；而且等终态会让调用方无法并发触发多个 target。

## Consequences

- 收益：长任务不占住调用方，对话轮次可以立刻继续，用户可以并发点多个磁贴。
- 收益：进度成为独立能力，后续做通知、托盘角标、跨设备看进展都接同一个通道。
- 代价：必须实现"终态必达"。推送丢帧时靠重进页面的快照查询与 `tasks/get` 补偿，这要求任务表可查、状态幂等。
- 代价：必须有节流。脚本 stdout 可能每秒几十行，逐行转成状态帧会打爆通道。
- 代价：调用方要知道"回执不等于完成"，这需要文档与提示词层面反复说明，否则模型会以为触发完就结束了。
- 被否决的方案一：同步等到终态。会让长任务占住一轮，且超时后调用方拿不到任何信息；也无法支持并发触发。注意 `runner.launch` 在 `requiresApproval` 时确实会同步回调一次 `onTerminal("input-required")`，这是"挂起"语义而非"终态"，不构成对本文的例外。
- 被否决的方案二：调用方轮询 `tasks/get`。实现简单，但延迟由轮询间隔决定，N 个磁贴就是 N 条轮询流；本机场景不存在"省连接"的收益。
- 被否决的方案三：改用 A2A `message/stream`。语义最正统，但本机已有 SSE 且控制台在用，为一次进度展示改造引入新协议路径不划算。
